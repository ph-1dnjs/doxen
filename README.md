## Doxen이 뭔가요?

Doxen은 **이미 저장소에 있는 Markdown 폴더를 문서 사이트로 바꿔 주는 npm 패키지**입니다.

새 문서 시스템으로 옮길 필요 없이, 지금 있는 폴더를 설정 파일에 연결하기만 하면 됩니다. 만들어지는 사이트에는 이런 기능이 들어 있어요.

- 상단 **탭** (예: 시작하기 / 작성 가이드 / 레퍼런스)
- 폴더별 **문서 탐색** 목록
- 자동 **목차**
- **한국어 전체 검색** (⌘/Ctrl + K) 과 검색 위치로 바로 이동
- 문서 안, 또는 지정한 섹션 안에서만 **찾기**

React나 Vue 같은 프레임워크를 프로젝트에 설치할 필요도 없습니다. 사이트를 그리는 코드는 전부 패키지 안에 들어 있어요.

---

## 시작 전 준비물

| 준비물 | 확인 방법 |
| --- | --- |
| **Node.js 22 이상** | 터미널에서 `node -v` 실행 → `v22.x.x` 이상이면 OK |
| npm 또는 Yarn | `npm -v` 또는 `yarn -v` |
| Markdown 문서를 둘 프로젝트 폴더 | 기존 저장소여도, 새 폴더여도 괜찮습니다 |

> 💡 Node 버전이 낮다면 [nvm](https://github.com/nvm-sh/nvm) 같은 버전 관리 도구로 22 이상을 설치하세요.

배포까지 하실 계획이라면 **Cloudflare 계정**도 필요합니다. 이건 [7단계](#7단계-비공개-사이트로-배포하기-cloudflare)에서 자세히 다룹니다.

## 1단계: 설치하기

문서를 붙일 프로젝트 폴더에서 아래 명령을 실행합니다. 개발용 도구이므로 `-D`(devDependencies)로 설치합니다.

**npm을 쓴다면**

```bash
npm install -D @unana_dev/doxen
```

**Yarn을 쓴다면**

```bash
yarn add -D @unana_dev/doxen
```

### 💡 `docs`와 `doxen`, 둘 다 같은 명령이에요

Doxen은 실행 명령을 두 가지 이름으로 제공합니다.

- `docs` — 짧고 편한 이름
- `doxen` — 다른 패키지와 이름이 겹칠 때 쓰는 이름

`docs`라는 이름은 흔해서 다른 의존성과 충돌할 수 있습니다. 그래서 `init`이 만들어 주는 스크립트는 **`doxen`을 사용**합니다. 헷갈리면 그냥 **항상 `doxen`을 쓰셔도 됩니다.**

---

## 2단계: 초기 설정 만들기 (init)

```bash
npx doxen init
# 또는
yarn doxen init
```

### init이 해주는 일

설정 파일이 아직 없다면 다음을 자동으로 준비해 줍니다.

- `docs.config.ts` — 사이트 설정 파일
- `docs/README.md` — 시작용 샘플 문서
- `package.json`에 스크립트 3개 추가: `docs:dev`, `docs:build`, `docs:deploy`
- `.gitignore`에 빌드 결과물과 `node_modules` 등록

### 안심하세요: 아무것도 덮어쓰지 않아요

`init`은 **기존 설정, 문서, 프로젝트 스크립트를 덮어쓰지 않습니다.** 이미 사용 중인 프로젝트에서 실행해도 안전합니다.

> 📁 **이미 문서 폴더가 있다면?**
> 설정 파일에서 경로만 기존 폴더로 바꿔 주고, 자동 생성된 시작 문서(`docs/README.md`)는 필요 없으면 지우면 됩니다.

## 3단계: 미리보기 띄우기 (dev)

```bash
npm run docs:dev
# 또는
yarn docs:dev
```

브라우저에서 **http://127.0.0.1:4173** 을 열어 보세요. 문서 사이트가 보이면 성공입니다! 🎉

Markdown 파일을 수정하고 저장하면 **브라우저가 자동으로 새로고침**됩니다.

**포트를 바꾸고 싶다면** (4173 포트를 이미 다른 프로그램이 쓰고 있을 때 등)

```bash
npx doxen dev --port 4200
```

> ⚠️ 로컬 미리보기에는 로그인/인증이 적용되지 않습니다. 배포 후 보호는 7단계에서 다룹니다.

## 4단계: 설정 파일 이해하기

`docs.config.ts`를 열어 보면 대략 이런 모양입니다.

```ts
// docs.config.ts
export default {
  title: '팀 문서',
  icon: { background: '#edf8ff', color: '#467792', border: '#bcdff8' },
  tabs: [
    { title: '시작하기',   dir: './guide',     slug: 'guide' },
    { title: '작성 가이드', dir: './writing',   slug: 'writing' },
    { title: '레퍼런스',   dir: './reference', slug: 'reference' },
  ],
};
```

> 💡 **자동완성을 받고 싶다면** `defineConfig`를 감싸서 쓰세요. 타입 힌트가 생겨서 오타를 줄일 수 있습니다.
>
> ```ts
> import { defineConfig } from '@unana_dev/doxen';
>
> export default defineConfig({
>   title: '팀 문서',
>   tabs: [ /* ... */ ],
> });
> ```

설정 파일은 `.ts`, `.mjs`, `.js` 중 아무거나 쓸 수 있습니다.

### tabs: 상단 탭 하나 = 문서 폴더 하나

| 항목 | 의미 | 규칙 |
| --- | --- | --- |
| `title` | 상단 탭에 보이는 이름 | 자유롭게 |
| `dir` | 이 탭에 보여줄 문서 폴더 | **설정 파일 기준 하위 폴더**여야 함 |
| `slug` | 문서 URL에 들어가는 이름 | **영문 소문자·숫자·하이픈**만, 탭끼리 **겹치면 안 됨** |

`dir`에서 자주 하는 실수:

```ts
dir: './guide'     // ✅ 설정 파일 옆의 guide 폴더
dir: './'          // ❌ 저장소 루트는 허용되지 않음
dir: '../shared'   // ❌ 설정 파일 바깥 폴더는 허용되지 않음
```

`slug`에서 자주 하는 실수:

```ts
slug: 'getting-started'  // ✅
slug: 'Guide'            // ❌ 대문자
slug: '시작하기'           // ❌ 한글
slug: 'my_docs'          // ❌ 밑줄
```

### icon: 로고와 파비콘 색상

상단 로고와 브라우저 탭 아이콘(파비콘)의 색을 정합니다. 두 가지 방법이 있어요.

**방법 1. 색 하나만 지정 (가장 쉬움)**

```ts
icon: '#eab308',
```

이 색을 기준으로 밝은 배경색, 중간 톤 테두리, 진한 글자색을 **알아서** 만들어 줍니다.

**방법 2. 하나하나 직접 지정**

```ts
icon: {
  background: '#edf8ff', // 배경색 (생략 시 #edf8ff)
  color: '#467792',      // 글자색 (생략 시 #467792)
  border: '#bcdff8',     // 로고 테두리 (생략 시 #bcdff8)
},
```

색상은 `#fff` 또는 `#ffffff` 형식의 **HEX 값**만 지원합니다.

### 문서 정렬 순서

탐색 목록은 **파일 이름순**으로 정렬됩니다. 숫자도 똑똑하게 인식해서 `2`가 `10`보다 앞에 옵니다. 순서를 정하고 싶다면 파일 이름 앞에 번호를 붙이세요.

```
guide/
├── 01-introduction.md
├── 02-installation.md
├── 03-first-page.md
└── advanced/
    └── 01-config.md
```

- 하위 폴더는 탐색 목록에 **경로 형태로** 표시됩니다.
- 숨김 파일(`.`으로 시작), `node_modules`, 심볼릭 링크 문서는 **제외**됩니다.

> ⚠️ **보안 메모**
> - 설정 파일은 Node에서 **실제로 실행되는 코드**입니다. 신뢰할 수 있는 저장소에서만 사용하세요.
> - 모든 탭은 **하나의 사이트에 함께** 들어갑니다. "이 탭은 A팀만 보기" 같은 탭별 권한은 없습니다.

## 5단계: 문서 작성 규칙

### 그대로 쓸 수 있는 것 ✅

- 표준 Markdown (제목, 목록, 강조 등)
- 코드 블록, 표
- 다른 문서로의 상대 링크 (`[설치 방법](./02-installation.md)`)
- 한국어 제목 앵커 (`#설치-방법`)
- 이미지·PDF 첨부: PNG / JPEG / GIF / WebP / AVIF / ICO / PDF

### 지원하지 않는 것 ❌

- 실행 가능한 HTML (HTML을 쓰면 **실행되지 않고 글자로** 보입니다)
- MDX
- YAML frontmatter (문서 맨 위 `---` 메타데이터)
- 확장 Markdown 플러그인

### 빌드가 실패하는 경우 🚨

이 두 가지는 **빌드를 멈추게** 하니 꼭 기억해 두세요.

1. **존재하지 않는 `.md` 파일로 링크했을 때** — 파일 이름 오타를 잡아 줍니다.
2. **문서 폴더 밖의 파일을 첨부했을 때** — 이미지는 문서 폴더 안에 두세요.

> 💡 링크 대상 파일은 검사하지만, 그 안의 **제목 앵커(`#어떤-제목`)가 실제로 있는지는 검사하지 않습니다.** 앵커 링크는 직접 눌러서 확인해 주세요.

### 목차는 자동으로

문서의 제목들이 자동으로 목차에 나타납니다. 같은 제목이 여러 번 나오면 앵커에 `-1`, `-2`가 붙습니다.

### 섹션 안에서만 검색하기: `:::search`

표가 긴 섹션에는 **그 섹션 전용 검색창**을 달 수 있습니다. 제목 **바로 아래**에 `:::search 영역 이름`을 쓰고, 끝에 `:::`로 닫으면 됩니다.

```markdown
## 1. 문서 작성

:::search 작성 방법 검색

| 작업 | 방법 |
| --- | --- |
| 제목 추가 | Markdown 제목 문법 사용 |
| 링크 추가 | 상대 경로 .md 링크 사용 |
:::
```

이렇게 하면 해당 영역에 검색창이 생기고, 검색어가 들어 있는 **표의 행만 남기고 나머지는 숨겨** 줍니다. (표 머리글은 그대로, 검색어를 지우면 모두 복원)

작성할 때 지킬 것:

- **번호가 있는 제목(`## 1. ...`)은 `:::search` 바깥**, 바로 위에 두세요.
- 한 문서에 검색 영역을 **여러 개 나란히** 둘 수 있습니다.
- 검색 영역 **안에 또 검색 영역을 넣지(중첩) 마세요.**
- 검색이 필요 없는 섹션은 그냥 평범한 Markdown으로 쓰면 됩니다.

### 검색은 이렇게 동작해요

| 종류 | 어디서 | 특징 |
| --- | --- | --- |
| **전체 검색** | 헤더 중앙, ⌘/Ctrl + K | 모든 탭의 제목·본문·표·코드 검색. 띄어쓴 단어를 **모두 포함**한 섹션을 찾고, 제목 일치를 먼저 보여 줌 |
| **문서 내 찾기** | 본문 상단 접이식 메뉴 | 현재 문서 안에서 찾기 |
| **섹션 검색** | `:::search` 영역 | 해당 섹션 안에서만 찾기 |

- 영문은 대소문자를 구분하지 않습니다.
- 한국어는 유니코드 정규화를 적용해서 비교합니다.
- 결과 사이 이동: 이전/다음 버튼, **Enter / Shift+Enter**
- 형태소 분석이나 오타 교정은 **하지 않습니다.** ("설치했다"로 "설치"를 찾는 식의 검색은 안 되니, 짧은 핵심 단어로 검색하세요.)

## 6단계: 정적 사이트로 빌드하기

```bash
npm run docs:build
# 또는
yarn docs:build
```

설정 파일 옆의 **`.docs-dist/`** 폴더에 완성된 정적 사이트가 생깁니다. 이 폴더를 원하는 정적 호스팅에 올리면 끝!

알아 두면 좋은 점:

- Doxen이 만든 표시가 있는 출력 폴더만 교체하니, 다른 폴더를 실수로 지울 걱정은 없습니다.
- 문서 변환에 실패하면 **이전에 성공한 결과를 그대로 유지**합니다.
- 사이트는 해시 URL(`#/...`)을 써서, `example.com/docs/` 같은 **하위 경로에 올려도 서버 설정 없이** 동작합니다.

설정 파일 위치가 기본과 다르다면 `--config`로 지정하세요. (`dev`, `deploy`, `ai` 명령에도 똑같이 쓸 수 있습니다.)

```bash
npx doxen build --config ./config/docs.config.ts
```

> ⚠️ **비공개 문서라면 주의!**
> 빌드 결과에는 문서 HTML과 **검색용 본문 전체**가 들어 있습니다. 원본이 비공개라면 결과물도 반드시 **비공개로** 배포하세요. 가장 쉬운 방법이 바로 다음 단계입니다.

## 7단계: 비공개 사이트로 배포하기 (Cloudflare)

사내 문서처럼 **허락된 사람만** 봐야 하는 경우, Doxen은 Cloudflare Pages + Cloudflare Access를 이용해 **명령 하나로** 비공개 배포를 해 줍니다.

```bash
npx doxen deploy
# 또는 npm run docs:deploy / yarn docs:deploy
```

- 처음 실행하면 **한국어 안내**를 따라 설정을 진행합니다.
- 두 번째부터는 같은 명령으로 **수정한 문서를 다시 배포**합니다.
- Wrangler(Cloudflare CLI)는 Doxen에 포함되어 있어서 **따로 설치할 필요 없습니다.**

> 이미 Doxen을 쓰던 프로젝트라 `docs:deploy` 스크립트가 없다면, `npx doxen init`을 한 번 더 실행하세요. 다른 것은 건드리지 않고 배포 스크립트만 추가됩니다.

### 7-1. 배포 전에 직접 해야 하는 일

자동화가 많이 되어 있지만, 아래 세 가지는 **본인이 직접** 해야 합니다.

- [ ] **Cloudflare 계정** 만들기
- [ ] Zero Trust를 처음 쓰는 계정이라면 **약관 동의와 플랜 선택** (Doxen은 유료 플랜을 구매하지 않습니다)
- [ ] **API 토큰 발급** (아래 권한 참고)

#### API 토큰 권한

토큰을 만들 때 **사용할 계정 하나만** 지정하고, 아래 4가지 **Account 권한**을 주세요.

| Account 권한 | 수준 | 왜 필요한가요? |
| --- | --- | --- |
| Account Settings | Read | 계정 조회 |
| Cloudflare Pages | Edit | 프로젝트 생성·배포 |
| Access: Apps and Policies | Edit | 접근 애플리케이션·허용 정책 생성·조회 |
| Access: Organizations, Identity Providers, and Groups | Edit | 팀 주소 확인·생성, 로그인 방법 준비 |

> ⚠️ 평소 쓰는 `wrangler login`(브라우저 로그인)만으로는 Access 자동 설정을 할 수 없습니다. **반드시 위 권한의 API 토큰**이 필요해요.

### 7-2. 첫 실행 흐름

`npx doxen deploy`를 처음 실행하면 다음 순서로 진행됩니다.

1. **Cloudflare 연결**
   안내되는 토큰 발급 화면에서 로그인해 토큰을 발급하고, 터미널의 입력란에 붙여넣습니다. (입력 내용은 화면에 가려져 보이지 않는 게 정상이에요.) 환경 변수를 직접 설정할 필요는 없습니다.

2. **계정 선택**
   접근 가능한 계정을 조회합니다. 여러 개라면 사용할 계정을 고릅니다.

3. **사이트 이름과 열람자 입력**
   새 사이트 이름과, 문서를 볼 사람들의 업무 이메일을 입력합니다.
   👉 **본인 이메일도 꼭 넣으세요!** 안 넣으면 본인도 못 봅니다.
   회사 로그인 방법(SSO 등)이 이미 있다면 그걸 고르고, 없으면 **이메일 일회용 코드 로그인**이 준비됩니다.

4. **내용 확인**
   계정·사이트·열람자·업로드할 문서 폴더를 확인하고 진행합니다.

5. **자동 준비 & 배포**
   Pages 프로젝트, 운영·미리보기용 Access 애플리케이션, 허용 이메일 정책, Fail closed 설정까지 만들고 검증한 뒤, 문서를 빌드해서 업로드합니다.

배포가 끝나면 꼭 **확인**해 보세요.

- [ ] 허용한 이메일로 로그인 → 문서와 첨부파일이 열리는지
- [ ] 허용하지 않은 이메일로 로그인 → 막히는지
- [ ] **운영 주소**와 **미리보기 주소** 둘 다 확인

> 실제 계정 로그인과 정책 전파는 자동 테스트로 검증할 수 없어서, 이 확인은 직접 하셔야 합니다.

### 7-3. 다음부터는 이 명령 하나

문서를 고쳤다면:

```bash
npx doxen deploy
```

사이트 이름이나 이메일을 다시 묻지 않고, 기존 정책을 확인한 뒤 바로 운영에 배포합니다. **Git push도 필요 없습니다.**

### 7-4. 열람자 추가·삭제하기

배포 설정은 설정 파일 옆 **`.doxen-deploy.json`** 에 저장됩니다. 열람자를 바꾸려면 이 파일의 `emails`만 고치고 다시 배포하세요.

```json
"emails": ["member@company.com", "new-member@company.com"]
```

```bash
npx doxen deploy
```

운영·미리보기 양쪽 정책에 자동으로 반영됩니다.

꼭 알아 둘 점:

- **이 JSON 목록이 기준**입니다. Cloudflare 대시보드에서만 추가한 이메일은 다음 배포 때 **지워집니다.**
- 이메일을 지워도 **이미 로그인한 세션은 바로 끊기지 않습니다.** 즉시 차단하려면 Cloudflare에서 활성 세션도 취소하세요.
- 이전 배포에는 당시 이메일 목록이 남아 있습니다. 필요하면 이전 배포도 삭제하세요. **롤백하면 이전 목록이 돌아올 수 있습니다.**
- Doxen이 만든 정책 외에 별도 정책·그룹·보안 조건이 있으면, 덮어쓰지 않고 **중단**합니다.
- 허용된 사람은 **사이트 전체**를 봅니다. 문서별·탭별 권한은 없습니다.

### 7-5. 토큰은 어디에 저장되나요?

| 환경 | 동작 |
| --- | --- |
| macOS / Linux | 저장할지 물어봅니다. 저장하면 `~/.config/doxen/accounts/<계정 ID>.json`에 **평문**으로 저장 (폴더 700, 파일 600 권한). OS 키체인은 아닙니다. |
| Windows | 자동 저장 없음 → 매번 입력 |

- 토큰이 만료되거나 권한이 거부되면 새 토큰을 입력하라고 안내합니다.
- 컴퓨터에서 토큰을 지우려면 위 계정 파일을 삭제하세요.
- **토큰 자체를 무효화**하려면 Cloudflare에서 토큰을 폐기해야 합니다.

`.doxen-deploy.json`에는 계정 ID, 사이트, 허용 이메일, Access 식별자가 들어가고 **API 토큰은 들어가지 않습니다.** 다만 팀 저장소에 커밋할 때는 **이메일 목록이 노출돼도 괜찮은지** 확인하세요.

### 7-6. CI에서 배포하기

CI(GitHub Actions 등)에서는 대화형 첫 설정을 할 수 없습니다. 그래서 순서는 이렇습니다.

1. **로컬에서** `npx doxen deploy`로 첫 설정을 끝내고 `.doxen-deploy.json`을 저장소에 둡니다.
2. CI의 비밀 환경 변수에 `CLOUDFLARE_API_TOKEN`을 등록합니다.
3. CI에서 `npx doxen deploy`를 실행합니다.

`CLOUDFLARE_ACCOUNT_ID`도 지정한다면 저장된 계정 ID와 **같아야** 합니다.

### 7-7. 중간에 실패했다면?

**같은 명령을 다시 실행하세요.** 이미 만든 자원의 식별자를 기억하고 있어서, 멈춘 단계부터 이어서 진행합니다.

- 설정이 끝나지 않은 동안에는 일반 `docs build`도 막힙니다. (보호 없는 빌드가 실수로 나가는 걸 방지)
- Doxen은 원격 자원을 **자동으로 삭제하지 않습니다.**
- 드물게 서버에는 자원이 생겼는데 응답을 못 받은 경우, 중복 생성을 막기 위해 Cloudflare 대시보드를 직접 확인해야 할 수 있습니다.
- 같은 이름의 Pages 프로젝트가 이미 있으면 **다른 이름**을 골라야 합니다. 기존 사이트를 가져가거나 덮어쓰지 않습니다.

### 7-8. 보호는 어떻게 동작하나요? (궁금한 분만)

배포 설정이 있으면 빌드 결과에 Pages 서버 인증 코드(`_worker.js`)와 라우팅 설정(`_routes.json`)이 함께 들어갑니다. 서버는 요청마다 Cloudflare Access의 JWT(서명·발급자·AUD·만료)와 허용 이메일을 확인한 뒤에만 파일을 내줍니다.

- HTML, `/site.json`, 이미지, PDF **전부** 보호됩니다.
- 인증에 실패하면 **403**으로 차단합니다.
- 응답은 `private, no-store`로 캐시되지 않게 설정됩니다. **Cache Rules로 이걸 덮어쓰지 마세요.**

주의할 점:

- 이 보호는 **Cloudflare Pages(Functions)** 에서만 동작합니다. 같은 빌드를 일반 정적 호스팅에 올리면 인증 코드가 실행되지 않습니다.
- 자동 설정은 기본 Pages 운영 주소와 미리보기 주소만 보호합니다. **커스텀 도메인**은 직접 연결하고 Access로 보호해야 합니다.
- 배포 이력·롤백·도메인은 **Cloudflare Pages**에서, 로그인·접근 정책은 **Cloudflare One의 Access**에서 관리합니다.

### 7-9. 수동 설정을 쓰던 분이라면

`docs.config.ts`에 직접 `deploy` 설정을 넣는 기존 방식도 계속 지원합니다.

```ts
deploy: {
  project: 'team-docs',
  access: {
    teamDomain: 'https://your-team.cloudflareaccess.com',
    audiences: ['0123456789abcdef...'],
    emails: ['member@company.com'],
  },
},
```

이 경우 호스트별 Access 정책과 Fail closed는 관리자가 직접 준비해야 합니다. **`.doxen-deploy.json`(자동)과 수동 `deploy` 설정을 동시에 두지는 마세요.**

## 보너스: AI로 문서 양식 맞추기

팀 문서의 형식을 통일하고 싶을 때, Doxen이 **AI 코딩 도구에 붙여넣을 작업 지침**을 만들어 줍니다.

```bash
npx doxen ai --file guide/writing.md \
  --instruction "현재 내용을 유지하고 문서 작성 방법을 표로 정리" \
  > /tmp/writing-prompt.txt
```

생성된 파일에는 표준 양식(**문서 정보 범위 → 번호별 단계 → 예외 → 관련 문서**), 기존 문서 내용, 요청이 함께 들어 있습니다.

사용 순서:

1. 위 명령으로 지침 파일을 만든다.
2. 내용을 사용 중인 AI 코딩 도구에 전달한다.
3. 결과를 검토해서 Markdown에 반영한다.
4. 미리보기와 `git diff`로 확인한다.

> 이 명령은 **AI API를 호출하지도, 파일을 고치지도 않습니다.** 지침 텍스트를 출력할 뿐이에요.
> 출력에는 기존 문서 전문이 포함되니, **원본 문서와 같은 공유 범위**로 다뤄 주세요.

## 자주 겪는 문제

**Q. `docs` 명령이 이상하게 동작해요.**
다른 패키지의 `docs` 명령과 이름이 겹쳤을 수 있어요. `npx doxen ...`을 사용하세요.

**Q. 파일을 고쳐도 미리보기가 갱신되지 않아요. / `EMFILE`, `ENOSPC` 에러가 나요.**
파일 감시 한도에 걸렸거나 네트워크 파일시스템을 쓰는 경우입니다. 폴링 모드로 실행하세요.

```bash
CHOKIDAR_USEPOLLING=1 npm run docs:dev
```

**Q. 빌드가 링크 오류로 멈춰요.**
존재하지 않는 `.md` 파일로 링크했거나, 문서 폴더 밖의 파일을 첨부한 경우입니다. 터미널 메시지에 나온 경로를 확인하세요. 로컬 파일 링크는 **현재 문서 기준 상대 경로**로 써야 합니다.

**Q. 설정 오류가 났어요.**
오류 내용은 터미널과 미리보기 화면에 함께 표시됩니다. 고친 뒤 새로고침하면 복구됩니다. `dir`이 하위 폴더인지, `slug`가 영문 소문자·숫자·하이픈인지 먼저 확인해 보세요.

**Q. 배포한 사이트가 로그인 화면 대신 403만 보여요.**
그 주소에 Access가 연결되어 있지 않은 경우입니다. 특히 **커스텀 도메인**이라면 Access로 직접 보호해야 합니다.

**Q. 이메일을 지웠는데 그 사람이 아직 볼 수 있어요.**
기존 로그인 세션이 남아 있는 겁니다. Cloudflare에서 해당 사용자의 활성 세션을 취소하세요.

**Q. 문서가 아주 많은데 괜찮을까요?**
사이트가 전체 문서 데이터를 한 번에 내려받는 구조라, 현재는 **소규모~중규모 팀 문서**에 맞춰져 있습니다. 대형 저장소는 성능을 미리 확인해 보세요.

## Doxen에 기여하고 싶다면

패키지 자체를 개발하거나 검증하려면 Doxen 저장소에서 다음 명령을 사용합니다.

```bash
npm ci
npm run dev            # 예제 사이트 실행
npm run check          # Node 테스트 + 문법 검사
npm run test:browser   # Chromium 브라우저 테스트
npm run test:package   # tgz를 별도 프로젝트에 설치해서 검증
npm run build          # 예제 정적 빌드
npm pack --dry-run     # 배포될 파일 목록 확인
npm pack
```

- 브라우저 테스트 전에 `npx playwright install chromium`을 먼저 실행하세요. 이미 설치된 Chrome을 쓰려면 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`에 실행 파일 경로를 지정하면 됩니다.
- 로컬에서 만든 패키지를 다른 프로젝트에 설치해 보려면, `npm pack`으로 만든 `.tgz` 경로를 패키지 이름 대신 넣어 설치하세요.
- npm 배포 파일은 `bin/`, `src/`, `client/`, README, LICENSE로 제한됩니다. 예제·테스트는 포함되지 않습니다.

**구조 한 줄 요약:** `bin/docs.js` → 설정 로더 → Markdown·섹션·첨부 처리 → 정적 빌드 또는 로컬 서버. 화면과 브라우저 검색 코드는 `client/`에 있습니다.
